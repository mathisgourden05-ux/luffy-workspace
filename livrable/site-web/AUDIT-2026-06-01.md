# 🏴‍☠️ Rapport d'audit — Road Spirit (site + app interne)

## 1. Verdict global

Le site est **présentable mais pas prêt pour de vrais clients ni pour une démo sérieuse au repreneur**. Le code fonctionne dans le scénario nominal (boutique, panier, mode démo de l'app), mais il reste **deux bugs bloquants**, un **trou de sécurité majeur côté base de données** (les données clients sont potentiellement lisibles par n'importe qui), une **promesse fausse** (le vendeur ne peut PAS vraiment gérer son catalogue sans toucher au code) et un **défaut visuel qui saute aux yeux** : plus d'un produit sur deux n'affiche pas sa vraie photo. Rien d'irréparable, mais l'ordre des corrections compte.

## 2. Problèmes CRITIQUES (à faire en premier)

### C1 — Sécurité : données clients exposées (aucune RLS sur commandes / réservations / profils)
**Fichier :** `interne/SUPABASE-SETUP.sql` (le script ne protège QUE la table `produits`)
**Ce qui cloche :** ton app lit les tables `commandes`, `reservations` et `profiles` (qui contiennent noms, emails, téléphones, adresses) avec la clé publique visible dans le code du site. Si ces tables n'ont pas de "RLS" (Row Level Security) activée avec des règles, **n'importe qui sur Internet peut récupérer toute ta base clients** via l'API Supabase. C'est une fuite RGPD.
**Correctif :** dans le dashboard Supabase, vérifier que RLS est **"Enabled"** sur `commandes`, `reservations`, `profiles`. Ajouter dans le SQL, pour chacune :
```sql
alter table public.commandes enable row level security;
create policy "commandes lecture connectes" on public.commandes
  for all to authenticated using (true) with check (true);
```
(idem `reservations` et `profiles`). **Aucune policy `select using(true)` publique** sur ces tables. Test : faire un GET anonyme sur `/rest/v1/commandes` → doit renvoyer vide/erreur.

### C2 — Droits d'écriture trop larges : n'importe quel compte connecté peut vider le catalogue
**Fichier :** `interne/SUPABASE-SETUP.sql` lignes 54-57
**Ce qui cloche :** la règle `produits ... for all to authenticated using(true)` donne à **tout compte connecté** le droit de supprimer en masse des produits, voire une catégorie entière en un clic (`deleteCategory`). Aucune séparation admin/vendeur côté base : le contrôle de rôle n'existe que dans l'interface, donc contournable depuis la console du navigateur. Un staff peut même se promouvoir admin (`update profiles set role='admin'`).
**Correctif :** séparer les règles par action — `select` public, `insert`/`update` pour les connectés, **`delete` réservé aux admins** via la table `profiles`. À coupler avec C5 (créer la table `profiles`).

### C3 — Synchro des catégories cassée : le vendeur NE PEUT PAS gérer son catalogue sans toucher au code
**Fichiers :** `boutique.html:246` (`CAT_MAP` en dur), `boutique.html:132-139` (onglets de filtre en dur), `produit.html:282`, `interne/app.html:1411-1417`
**Ce qui cloche :** la boutique mappe les catégories via un dictionnaire **figé dans le code**. Si le vendeur crée une catégorie « casques » dans l'app, le produit est silencieusement reclassé en « Accessoire » sur la boutique, et **aucun nouvel onglet de filtre n'apparaît**. Pire, les catégories sont stockées en `localStorage` (donc liées à un seul navigateur : une catégorie créée sur le PC n'existe pas sur le Mac). La promesse « le vendeur gère seul son catalogue » est fausse dès qu'il ajoute une catégorie.
**Correctif :** rendre les filtres **dynamiques** — dériver la liste des catégories depuis les produits réellement chargés (`new Set(produits.map(p=>p.categorie))`) et générer les onglets + le `<select>` à partir de ça. Supprimer le repli muet vers `'accessoire'`. La seule source de vérité = la colonne `categorie` de Supabase, pas le `localStorage`.

### C4 — Colonne `disponible` mal définie : un produit en rupture reste affiché et achetable
**Fichier :** `interne/SUPABASE-SETUP.sql` lignes 22 et 40
**Ce qui cloche :** le SQL crée `disponible boolean default true` comme colonne fixe, **non liée au stock**. Sur une base neuve, tous les produits (même à stock 0) sont `disponible=true`. Or la boutique filtre sur `disponible=true` → **un article en rupture s'affiche et reste achetable**. Mettre stock=0 dans l'app ne le retire pas. Ça contredit ton schéma de prod (où `disponible` est calculé depuis le stock).
**Correctif :** définir la colonne comme **générée** :
```sql
disponible boolean generated always as (stock > 0) stored
```
Comme `add column if not exists` ne re-type pas une colonne existante, prévoir un bloc qui la supprime puis la recrée en version générée. Vérifier que rien n'écrit cette colonne (déjà le cas dans l'app).

### C5 — Table `profiles` utilisée par l'app mais jamais créée par le SQL
**Fichier :** `interne/app.html` (lignes 825, 1513, 1529) — absente de `SUPABASE-SETUP.sql`
**Ce qui cloche :** l'app lit/écrit `profiles` pour déterminer les rôles après connexion. La table **n'est créée nulle part**. En prod, après un vrai login, le rôle n'est jamais résolu → l'accès « Équipe » est bloqué et tout utilisateur est traité en « Staff » par défaut.
**Correctif :** ajouter à `SUPABASE-SETUP.sql` la création de `public.profiles` (id, prénom, nom, role, created_at), sa RLS, et un trigger qui crée automatiquement une ligne à chaque inscription. Documenter l'étape dans `GUIDE-SUPABASE.md`.

### C6 — Bug bloquant : la page paiement plante au chargement
**Fichier :** `paiement.html:637`
**Ce qui cloche :** le code appelle `document.getElementById('successOverlay').classList...` mais **cet élément n'existe pas** dans le HTML (seules les règles CSS `.success-overlay` existent). `getElementById` renvoie `null` → **erreur JS à chaque chargement**. Conséquence : un visiteur arrivant sur `paiement.html` avec un panier vide reste **bloqué sur un formulaire vide** (la redirection ne s'exécute jamais). *Vérifié dans le code.*
**Correctif :** simplifier la condition (l'overlay est mort, le succès passe par `confirmation.html`) :
```js
if(getCart().length===0){ setTimeout(function(){window.navigate('boutique.html');},100); }
```
Et nettoyer les règles CSS `.success-overlay` devenues inutiles (lignes 143-148).

### C7 — Bug bloquant : page Réservations en lecture seule (boutons morts)
**Fichier :** `interne/app.html:1170-1173`
**Ce qui cloche :** les boutons « Statut » et « Suppr. » sont rendus **sans `onclick`**. Les fonctions `openModalRes()` et `deleteRes()` existent mais ne sont jamais appelées. Résultat : **impossible de gérer les demandes d'essai clients**, alors que c'est la raison d'être de la page.
**Correctif :** câbler les boutons :
```html
<button class="btn-action" onclick="openModalRes('${r.id}','${r.statut}')">Statut</button>
<button class="btn-action danger" onclick="deleteRes('${r.id}')">Suppr.</button>
```

## 3. Problèmes ÉLEVÉS

### E1 — 86 produits sur 150 (57 %) n'affichent pas leur vraie photo
**Fichier :** `catalogue-roadspirit.json` (et son doublon `catalogue-data.js`)
**Ce qui cloche :** seulement **97 images distinctes pour 150 produits**. Une même photo de gant sert à 6 produits, une image de magnet illustre des coques iPhone, des pin's et une boucle de ceinture. Le client voit des articles différents avec la même image → confusion, réclamations « reçu ≠ photo », rendu peu pro. **C'est le défaut le plus visible du site.**
**Correctif :** récupérer les vraies URL d'images depuis l'export WooCommerce de roadspirit.fr (ou Triumph officiel), en priorisant les produits chers (blousons 540 €, bottes). À défaut, afficher un visuel neutre « photo à venir » plutôt qu'une image trompeuse. Supprimer les produits obsolètes (coques iPhone 6+, Galaxy S5).

### E2 — Catalogue dupliqué en deux fichiers identiques (à maintenir en double)
**Fichiers :** `catalogue-data.js` ≡ `catalogue-roadspirit.json` (0 différence)
**Ce qui cloche :** les deux fichiers contiennent exactement les mêmes 150 produits. Toute correction (photo, prix) doit être faite **deux fois**, sinon ils divergent en silence.
**Correctif :** garder le `.json` comme **seule source**, générer le `.js` automatiquement (petit script : `window._rs_catalogue = ` + contenu du JSON). Documenter lequel est généré pour interdire l'édition manuelle.

### E3 — Faille XSS dans l'app interne (et plus modérément sur la boutique)
**Fichier :** `interne/app.html` (toutes les fonctions `render*`), `boutique.html:325-347`
**Ce qui cloche :** les noms de produits, catégories et données clients sont injectés directement en HTML (`innerHTML = ...${champ}...`) **sans échappement**. Un nom de produit contenant `<img src=x onerror=...>` exécute du code dans l'app admin (vol de session, auto-promotion admin). La fonction `esc()` existe mais n'est presque jamais utilisée — et elle est **incomplète** (n'échappe ni `>` ni `'`).
**Correctif :** compléter `esc()` :
```js
function esc(s){return String(s).replace(/&/g,'&amp;').replace(/</g,'&lt;').replace(/>/g,'&gt;').replace(/"/g,'&quot;').replace(/'/g,'&#39;');}
```
puis l'appliquer à **toute** valeur dynamique : `${esc(p.nom)}`, `${esc(c.client_nom)}`, etc. Idem côté boutique sur `p.nom` et `p.image`.

### E4 — Bouton « Modifier » de l'app casse dès qu'un nom contient une apostrophe
**Fichier :** `interne/app.html:1281`
**Ce qui cloche :** `onclick="editProduit(${JSON.stringify(p)...})"` injecte tout l'objet produit dans l'attribut HTML. Un produit nommé « Gants d'été » ou « Blouson <Pro> » **casse le bouton** (et ouvre une porte XSS, cf. E3).
**Correctif :** ne pas sérialiser l'objet. Mettre `onclick="editProduit('${p.id}')"` et récupérer le produit par son id : `allProduits.find(x=>String(x.id)===String(id))`.

### E5 — Aucune protection « mode démo » sur les écritures Supabase
**Fichier :** `interne/app.html` (save produit, deleteProduit, import CSV, toggleRole, save statuts…)
**Ce qui cloche :** seul `quickStatus` gère le mode démo. Les autres fonctions d'écriture tentent une vraie insertion Supabase même en démo → échec sur RLS ou modification non voulue de la prod pendant une présentation.
**Correctif :** ajouter en tête de chaque fonction d'écriture :
```js
if(isDemoMode){ toast('Action indisponible en démo'); return; }
```

### E6 — Données de démo désynchronisées de l'affichage du stock
**Fichier :** `interne/app.html:736-741` vs `1273-1279`
**Ce qui cloche :** la démo fournit `reference`, mais l'affichage lit `ref_g8` (→ toujours « — »), `type` (absent → badge vide) et `disponible` (absent → **tout affiché « Rupture »** même avec du stock). C'est exactement ce qu'un repreneur verrait en démo locale.
**Correctif :** aligner les clés démo sur le schéma réel, ou rendre l'affichage tolérant : `const dispo = p.disponible ?? (p.stock>0)`.

### E7 — Labels de formulaire non reliés aux champs (accessibilité)
**Fichiers :** `services.html:237-266`, `paiement.html` (lignes 305, 313, 317, 323)
**Ce qui cloche :** les `<label>` n'ont pas d'attribut `for` et les champs pas d'`id`. Lecteurs d'écran muets, clic sur le label inopérant. Échec WCAG.
**Correctif :** `<label for="c-prenom">Prénom</label><input id="c-prenom" ...>` sur chaque champ.

### E8 — Pas d'image de partage (og:image) sauf sur l'accueil
**Fichiers :** toutes les pages sauf `Road Spirit.html`
**Ce qui cloche :** partager la boutique, une moto ou un produit sur WhatsApp/Messenger/LinkedIn affiche un aperçu **sans visuel** → mauvais effet pour un site qu'on veut montrer à un repreneur.
**Correctif :** ajouter `<meta property="og:image" content="https://.../image-1200x630.jpg">` dans le `<head>` de chaque page (réutiliser celle de l'accueil par défaut).

## 4. Problèmes MOYENS / FAIBLES (groupés)

**Comportement boutique / panier**
- Bouton panier incohérent selon la page (`Road Spirit.html:450` mène à la boutique au lieu du panier ; `panier.html:272` renvoie vers la boutique). → uniformiser : l'icône panier mène toujours à `panier.html`.
- Badge panier de l'accueil figé à « 0 », jamais mis à jour (`Road Spirit.html:452`). → recalculer depuis `localStorage` au chargement.
- Produits ajoutés depuis l'accueil ont `id:null` → lien « Voir le produit » cassé (`produit.html?id=null`). → leur donner un vrai id ou masquer le lien.
- Toast « ajouté au panier » affiché même quand l'ajout n'a pas eu lieu (`boutique.html:310-313`). → message neutre dans ce cas.

**Données catalogue (à corriger dans les DEUX fichiers tant que E2 n'est pas réglé)**
- `id60 GANTS PEAK` : badge « -30 % » affiché mais `prix_promo=null` → fausse promo, prix plein. → mettre `prix_promo=73.01` ou `remise=0`.
- `id80 JEANS CONNECTOR` classé en « accessoires » au lieu de « jeans_pantalons » → invisible au filtre jeans.
- Métadonnées `meta` fausses (`images_disponibles=124`, note « images null » obsolète alors que 0 image null). → corriger à 150 et réécrire la note.
- 2 prix promos avec arrondi non standard (`id28`, `id50`). → mineur.

**Supabase / import**
- Import CSV : upsert **ligne par ligne** (150+ requêtes lentes et fragiles) + `onConflict:'ref_g8'` sans contrainte UNIQUE en base → doublons possibles. → un seul upsert groupé + créer l'index unique. Catégorie forcée à « Autre » (cf. C3).
- Parsing CSV naïf (`split(';')`, `split('\n')`) → casse sur guillemets, BOM, CRLF. → normaliser + utiliser PapaParse.
- `rsLoadProduct` n'applique pas le filtre `disponible` (`catalogue-supabase.js:90`) → produit en rupture accessible par URL directe.

**Cohérence métier / sécurité paiement**
- Adresse contradictoire sur `services.html:283-284` : la carte pointe « 142 avenue de la Mer, Toulon » au lieu de l'adresse canonique « Espace Mermoz, 212 chemin des Delphiniums, 83190 Ollioules ». → **à corriger, ça envoie le client à la mauvaise adresse.**
- Paiement entièrement côté client : prix/quantités dans `localStorage`, envoyés bruts. La future fonction Stripe **ne doit jamais faire confiance au prix reçu** : relire prix et stock côté serveur depuis Supabase. (À garder pour le TODO « paiement réel ».)
- Champs CB maison sur `paiement.html` alors que c'est annoncé « Paiement sécurisé Stripe » → supprimer et passer par Stripe Checkout/Elements.

**Accessibilité / responsive / SEO (faible)**
- Animation hamburger morte sur pages secondaires (JS togggle `open`, CSS attend `o`) — purement cosmétique.
- Hamburger sans `aria-expanded`/`aria-controls` ; `panier.html:92` sans `aria-label`.
- Filtre prix de la boutique masqué sous 900px (`display:none`) → indisponible sur mobile.
- Breakpoints incohérents d'une page à l'autre (540/600/640/700px) → harmoniser via `shared.css`.
- Couleur `--muted` (#6E6B78) sous le seuil de contraste AA → éclaircir vers ~#9A98A4.
- Pas de `canonical` ni `og:url` → risque de doublon SEO avec le vrai roadspirit.fr.
- `confirmation.html`/`paiement.html` devraient être en `noindex`.
